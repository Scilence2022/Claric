Word AI Redliner

Technical Architecture

Technical architecture of an AI-powered Microsoft Word add-in that applies LLM-suggested edits as native tracked changes. This post focuses on the intermediate representation that bridges the gap between Word's object model and LLM text processing.

1. The Problem

Microsoft Word documents are not flat text. They are deeply nested XML structures (OOXML) where every paragraph carries style metadata, list numbering, table membership, and character-level formatting runs. An LLM, however, operates on plain text strings.

The core engineering challenge is: how do you send a Word document to an LLM, get back amended text, and apply those amendments as word-level tracked changes—without destroying the document's formatting, structure, or semantic markup?

Word AI Redliner solves this with a structured intermediate representation (IR) that preserves document semantics through a parse → chunk → dispatch → reassemble pipeline.

The add-in runs as an Office.js taskpane inside Word's WebView2 container. Two LLM backends are supported via OpenAI-compatible /v1/chat/completions endpoints: a local vLLM instance (Qwen 3.5-35B-A3B) and Ollama. 3. The Intermediate Representation

The IR is the central data structure of the system. It consists of three layers, each progressively further from the Word object model and closer to LLM-compatible text.

3.1 Layer 1: DocumentModel (Parsed Paragraphs)

The document parser (document-parser.js) traverses the active Word document via Office.js and produces a DocumentModel—an array of ParsedParagraph objects:

// ParsedParagraph — the atom of the IR
{
  index: 42,              // Original paragraph index in document
  text: "The Seller shall...",
  headingLevel: 0,        // 0 = body, 1-9 = heading level
  style: "TitleClause",   // Custom Word style name
  styleBuiltIn: "Normal", // Built-in style enum
  isListItem: true,
  listString: "(a)",      // Bullet/number prefix
  listLevel: 1,           // Nesting depth
  inTable: false,
  tokenEstimate: 47       // ceil(chars / 4)
}

This is the foundational IR. Every downstream module operates on paragraph index references back to this model. The parser uses a batched load pattern with four sequential context.sync() calls to minimize Office.js round-trips:

  1. Load paragraph collection items
  2. Load text, style, styleBuiltIn, isListItem for all paragraphs
  3. Load listItem details (level, listString) for list paragraphs
  4. Load parentTableOrNullObject for table membership detection

Heading detection fallback chain

Legal documents frequently use custom styles rather than Word's built-in Heading1–Heading9. The parser applies a three-tier fallback to classify headings:

TierSourceExample
1 Built-in stylestyleBuiltInHeading2 → level 2
2 Custom style mappingstyle nameTitleClause → level 2, Schedule → level 1
3 Text pattern inferenceParagraph textARTICLE IV → level 1, short ALL-CAPS → level 2

Tier 3 only fires for paragraphs with no custom style applied (Normal or empty), preventing false positives on styled body text.

3.2 Layer 2: DocumentChunk (Token-Budgeted Segments)

The chunker (document-chunker.js) splits the DocumentModel into DocumentChunk[]—segments sized for LLM context windows:

// DocumentChunk — the unit of LLM dispatch
{
  id: "chunk-3",
  paragraphs: [ParsedParagraph, ...],  // References to Layer 1
  startIndex: 42,                       // First paragraph index
  endIndex: 67,                         // Last paragraph index
  tokenCount: 11200,                    // Sum of paragraph estimates
  sectionTitle: "ARTICLE IV — ...",     // Nearest heading (for logging)
  overlapBefore: "...prior context..."  // Tail of previous chunk
}
Design decision: Chunks reference paragraph objects from the DocumentModel rather than copying text. This means the chunk's startIndex / endIndex remain valid pointers into the Word document's paragraph collection throughout the pipeline. These indices are used later by the reassembler to create bookmarks on exact paragraph ranges.

The chunking algorithm enforces three structural constraints:

  1. Heading boundaries. H1/H2 headings are primary split points. A chunk always starts at a heading boundary when possible, so the LLM sees complete logical sections.
  2. Table atomicity. Consecutive inTable=true paragraphs are accumulated as an indivisible unit. Tables are never split mid-way through.
  3. Token budget. Each chunk targets a maximum of 12,000 tokens (configurable). When no heading boundary exists, the chunker falls back to paragraph-boundary splitting. A minimum threshold (500 tokens) prevents tiny fragments from becoming their own chunks—trailing runts are merged into the previous chunk.

Overlap for continuity

Each chunk after the first carries an overlapBefore field containing the text of the previous chunk's last paragraph(s). This overlap is injected into the LLM prompt with explicit markers:

[CONTEXT - DO NOT AMEND]
...last paragraph of previous chunk...
[END CONTEXT]

[AMEND THIS TEXT]
...this chunk's paragraphs...
[END TEXT]

The markers serve a dual purpose: they provide semantic continuity for the LLM (it can see the clause context it just left) while explicitly fencing the non-editable region. A post-processing step (stripChunkDelimiters) removes these markers if the LLM echoes them.

3.3 Layer 3: ChunkResult (LLM Response + Metadata)

After parallel LLM dispatch, each chunk yields a ChunkResult:

// ChunkResult — the output of LLM processing
{
  chunkId: "chunk-3",
  chunkIndex: 3,
  status: "fulfilled",       // | "rejected" | "cancelled"
  amendment: "The Seller...",  // Amended text (or null)
  comment: "Risk: ...",        // Comment text (or null)
  error: null,
  chunk: DocumentChunk         // Back-reference to Layer 2
}

The three statuses follow Promise.allSettled semantics: a failed chunk does not block successful ones. The orchestrator tracks per-chunk timing for real-time ETA calculation and reports progress after each chunk completes.

4. Context Extraction

Before chunks are sent to the LLM, a context extractor (context-extractor.js) scans the full DocumentModel to build a DocumentContext object:

{
  definitions: [
    { term: "Seller", definition: "\"Seller\" means Acme Corp...", paragraphIndex: 12 },
    ...
  ],
  abbreviations: [
    { abbreviation: "SPA", expansion: "Share Purchase Agreement", paragraphIndex: 3 },
    ...
  ],
  outline: [
    { level: 1, text: "ARTICLE I — DEFINITIONS", paragraphIndex: 0 },
    { level: 2, text: "Section 1.1 Definitions", paragraphIndex: 1 },
    ...
  ]
}

Definitions are extracted using eight regex patterns covering legal drafting conventions: "Term" means..., (the "Term"), (hereinafter "Term"), colon-delimited definitions, and more. Abbreviations are detected via the (XX) parenthetical pattern, with initial-matching expansion extraction.

The context is formatted into a text prefix and prepended to every chunk's system message. Critically, it is filtered per-chunk: only definitions whose term appears in the chunk text are included, keeping the prefix within a 4,000-token budget.

5. Parallel LLM Dispatch

The orchestrator (orchestrator.js) implements a worker-pool concurrency pattern. N workers (default 4) pull from a shared index, each processing one chunk at a time:

Each worker composes a message array per chunk:

  • System message: User's context prompt template + filtered document context prefix (definitions, abbreviations, outline)
  • User message: Active amendment/comment prompt template with {selection} replaced by the chunk text (with overlap markers)

An AbortController signal threads through every worker, enabling instant cancellation. The controller avoids AbortSignal.any() (unsupported in Office's WebView2 runtime), manually wiring external abort signals to local controllers.

6. Response Post-Processing

LLM output passes through a cleaning pipeline before reaching the reassembler:

StageFunctionPurpose
1stripThinkTagsRemove <think>...</think> reasoning artifacts (4-pass regex: complete blocks, orphaned closers, orphaned openers, whitespace collapse)
2parseDelimitedResponseSplit ===AMENDMENT=== / ===COMMENT=== sections for merged mode
3stripMarkdownRemove bold, italic, heading markers, code fences, bullet asterisks (preserves numbered lists common in contracts)
4stripChunkDelimitersRemove echoed [AMEND THIS TEXT] / [END TEXT] markers

A truncation guard rejects LLM output that is less than 30% the length of the original chunk text, preventing silently truncated responses from destroying document content.

7. Reassembly: IR Back to Word

The reassembler (reassembler.js) is where the IR is converted back into Word document mutations. This is the most complex module, because it must bridge the text-oriented LLM output with Word's paragraph-level object model.

7.1 Bookmark Persistence

Before any LLM calls begin, the reassembler creates hidden bookmarks on each chunk's paragraph range:

// For each chunk:
startRange = paragraphs[chunk.startIndex].getRange('Start')
endRange   = paragraphs[chunk.endIndex].getRange('End')
fullRange  = startRange.expandTo(endRange)
fullRange.insertBookmark("_wdp" + hex(timestamp) + hex(index) + random)

Bookmarks are prefixed with _ (hidden in Word's UI) and use hex timestamps to ensure uniqueness. They persist across context switches and Word API sessions, surviving the potentially long LLM processing time.

7.2 Paragraph-Level Alignment (LCS + Similarity)

The central algorithm of reassembly is _alignParagraphs, which maps LLM output paragraphs back to original document paragraphs. It uses a two-phase approach:

Phase 1: LCS on exact (trimmed) text matches ────────────────────────────────────────────── Original: [A] [B] [C] [D] [E] [F] Amended: [A] [B'] [X] [D] [E'] [F] LCS anchors: A ─── D ─── F (exact matches) Phase 2: Greedy forward matching in gaps ────────────────────────────────────────────── Gap 1 (between A..D): Orig: [B] [C] Amended: [B'] [X] B↔B' similarity=0.82 → keep (modified) C has no match → delete X has no match → insert Gap 2 (between D..F): Orig: [E] Amended: [E'] E↔E' similarity=0.71 → keep (modified) Result ops: keep(A), keep(B↔B'), delete(C), insert(X), keep(D), keep(E↔E'), keep(F)

Figure 3: Two-phase paragraph alignment. LCS finds exact anchors; greedy matching fills gaps with a 0.4 similarity threshold.

The similarity function uses word-level set overlap: |shared words| / max(|words_a|, |words_b|). A threshold of 0.4 captures paragraphs where the LLM has substantively rewritten content while avoiding false matches between unrelated paragraphs.

The alignment produces an operation sequence: keep (paragraph pair, possibly with text edits), delete (original paragraph removed), insert (new paragraph added).

7.3 Applying Changes in Reverse Document Order

Amendments are applied from the end of the document forward. This is critical: inserting or deleting paragraphs shifts all subsequent paragraph indices. By processing in reverse order, earlier ranges remain valid.

For each alignment operation:

  • keep with text difference: Applies word-level diff within the single paragraph using the office-word-diff library's token-map strategy. At paragraph scope, this preserves character-level formatting (bold, italic, font, color) while generating tracked changes. Falls back to full text replacement if the word-level diff fails.
  • delete: Calls paragraph.delete(), which generates a tracked deletion in Word.
  • insert: Calls anchorParagraph.insertParagraph(text, 'After'), which generates a tracked insertion.
Why paragraph-level, not range-level? The initial implementation used range-level text replacement (replacing the entire chunk range at once). This destroyed paragraph boundaries, list numbering, heading styles, and table structure. The paragraph-level strategy preserves all OOXML paragraph properties (w:pPr) because each paragraph's properties are untouched—only the text runs within are modified.

7.4 Comment Insertion

Comments are inserted in a separate phase after all amendments complete. This ordering is required because Word's tracked-changes mode (ChangeTrackingMode.trackAll) can cause AccessDenied errors when inserting comments on ranges that contain pending tracked changes. The reassembler explicitly disables change tracking before the comment phase.

8. The Diff Engine

Word-level tracked changes are produced by the office-word-diff npm package, which implements a cascading strategy:

StrategyMechanismPreservesScope
Token MapSplits paragraph into Word.Range objects via getTextRanges([" "]), maps each word to its range, applies insertions/deletions per-wordCharacter-level formatting (bold, italic, font, color)Single paragraph
Sentence DiffTokenizes by sentence boundaries, computes diff, applies at sentence granularityParagraph structureSingle paragraph (fallback)
Block ReplaceFull range.insertText(text, 'Replace')Nothing (last resort)Full range

The ParagraphBlock model (structure-model.js) maintains the token map: an array of { text, range: Word.Range } objects. This allows the diff engine to map individual word changes to their exact Word.Range in the document, producing surgical tracked changes without touching surrounding formatting.

9. The Four-Category Prompt System

The PromptManager maintains four independent prompt categories, each with its own CRUD, activation state, and localStorage persistence:

CategoryRole in LLM MessagePlaceholder
ContextSystem message (static preamble)None
AmendmentUser message (rewriting instructions){selection}
CommentUser message (analysis instructions){selection}
SummaryUser message (summarization instructions){comments}, {whole document}, {tracked changes}

Amendment and comment are mutually exclusive (activating one deactivates the other). However, a merged mode allows both in a single LLM call: the amendment prompt's commentInstructions field appends delimiter instructions, and the response parser splits the output on ===AMENDMENT=== / ===COMMENT=== markers.

10. Summary Document Generation

The summary workflow extracts comments, document text, and tracked changes from the active document; composes a prompt with placeholder substitution; sends it to the LLM; and creates a new Word document with the formatted result.

Tracked changes are extracted via OOXML parsing: body.getOoxml() returns the raw XML, which is parsed with the browser's DOMParser. The parser handles the pkg:package wrapper, normalizes w:proofErr elements, pairs adjacent w:del/w:ins elements (same author) as replacements, and detects move operations via w:moveFrom/w:moveTo.

LLM markdown output is converted to HTML via marked.parse(), with inline table border styles injected (Word's insertHtml renders borderless tables by default). The HTML is inserted into a new document created via context.application.createDocument().
