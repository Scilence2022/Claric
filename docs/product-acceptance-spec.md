# Claric 产品验收规格

本规格定义发布证据，不是已通过的测试报告。依据 [README](../README.md)、[架构说明](../ARCHITECTURE.md)、[安全策略](../SECURITY.md) 的产品承诺，以及 [harness 分析报告](harness-analysis-report.md) 对旧开发端点的调查。源码、脚本和实际运行结果优先于历史报告中的行号、测试数量与推断。修改承诺或执行链时同步更新本规格。

## 四层证据

| 层级 | 必须保存的证据 | 能证明什么 | 不能替代什么 |
|---|---|---|---|
| L1 静态契约 | 提交号、工作树差异、承诺到源码/测试的映射、lint/typecheck 输出 | 配置、接口和约束可追溯，静态检查通过 | 不证明代码已执行、真实服务或 Word 可用 |
| L2 自动化行为 | 完整 Jest/coverage/check-coverage 输出、测试与跳过数量、失败明细；受控输入与 mock 边界 | 纯逻辑、UI 状态、Word API 调用意图与错误路径符合断言 | mock Word、jsdom、覆盖率百分比不是宿主渲染、修订或模型质量证据 |
| L3 构建与部署 | 本次 production build、verify-build 输出、dist 指纹、部署地址、manifest、静态资源/代理请求结果；发布容器的构建和扫描结果 | 验证的是交付字节、资源可加载、部署/传输路径实际可达 | schema 测试、健康检查、服务器日志不能证明 Word 完整流程 |
| L4 真实 Word 产品验收 | 下表逐项记录的宿主/版本、输入文档、操作录像或截图、结果文档和观察 | 指定平台、模型、设置与构建下的真实产品行为 | 不自动推广至其他平台、模型、语言、文件或版本 |

`npm run verify` 当前执行 `lint → test → coverage → check-coverage → typecheck → build → verify-build`。CI 另有生产依赖审计、容器构建及 Trivy 门禁；本地 verify 不等价于完整 CI，也不包含 L4。

覆盖率只对配置收集范围负责，三个分组独立设门禁；不能用全局通过掩盖 UI 分组退化。summary 必须可读取/解析且结构合法，参与计算的计数和阈值必须为有限数值；计数满足 `0 <= covered <= total`，分组每项 `total > 0`，阈值在 `[0, 100]`。单文件没有函数或分支时合法的 `0/0` 不构成通过证据，必须由组内其他文件提供非零分母。不得降低既有阈值来制造绿灯。

## 授权与写入契约

- 默认 `autoApplyChanges=false`。提案展示、定位或取消不得被描述为应用成功；关闭自动应用时须由用户选择并应用，未选中/拒绝的修改不应写入。
- 用户主动开启自动应用构成持续授权，设置持久化；此模式会在回合结束后对待处理提案顺序应用，不再等待逐卡点击。提案仍须可审查，不能宣传为“任何修改都必须逐卡确认”。验收要记录开启/关闭动作、重载后的状态和回合中途切换的实际效果。
- `src/taskpane/ui/chat-view.js` 在提案入队时检查开关，并在收尾后的每张卡实际执行前复查授权、跟踪设置、回合错误和 pending 状态。关闭开关阻止剩余队列继续写入；关闭或取消不撤销已经提交给 Word 的修改。启用使用 DOM 确认对话框，跟踪关闭时不得授予自动应用权限。
- 自动应用仍须走应用校验和跨卡写入互斥；重试、重复点击、多个提案和取消不应造成重复或并发写入。错误不能冒充成功，已发生的部分写入也不能被笼统称作“全部回滚”。
- 跟踪修订设置、用户授权和 Word 原生修订是不同契约。分别记录开启/关闭跟踪时的结果及原跟踪模式恢复；表格结构、图片与格式操作存在宿主差异，不能笼统承诺所有操作都形成可接受/拒绝的修订。
- 保留格式是待验证的产品目标，不是任意 OOXML、复杂嵌套表格或所有 Word 版本的无损保证。超出能力范围时应有明确提示，不能静默破坏文档。
- 摘要新建文档、MCP 外部工具等操作单独记录授权与副作用边界，不能借“提案模式”推断其与当前文档编辑具有相同事务语义。

## 构建物与旧 Harness

每轮验收先运行本次 `npm run build && npm run verify-build`，保留 `dist/build-info.json` 的 `hash`、`builtAt`、`mode`、`appVersion` 及命令日志。verify-build 必须检查必需资源、schema 并重新计算产物指纹。当前 `tests/build-info.spec.js` 使用独立 fixture 验证校验器，普通单测不再依赖遗留 dist；真实生产包仍须另跑构建后检查。指纹用于字节归因，不是签名或安全认证，也不独立证明源提交关系。

部署后核对 manifest URL、HTTPS 信任、taskpane/commands、动态模块、PDF worker 和图标实际加载；以部署字节及 Word Activity 中报告的指纹对应本次构建。缓存旧文件、指纹缺失或无法关联本次提交时，标为未验证而不是假定最新版。构建预算成功不代表交互性能通过。

旧 `scripts/dev-e2e-middlewares.cjs` 是 webpack 开发服务器的服务端协议，受 `ENABLE_DEV_ENDPOINTS=true` 显式开关控制，默认关闭，不属于生产静态服务器。harness 报告中的调查状态是：客户端驱动未入仓、静态用例缺失、未接 CI，已有 smoke 日志只证明当时局部连通。不得把存在端点、循环 trigger 成功、空用例返回或历史日志称作完整 E2E 通过。恢复使用必须提供版本化驱动、非空脱敏用例、真实 Word 结果与构建关联；本规格不宣告旧 harness 已恢复或已删除。

本轮开发端点已加入 token、精确 Origin、有界原子 snapshot、runId claim/complete 和协议测试，迁移见 [本地协议](dev-harness-protocol.md)。不再使用 wildcard CORS 或全局进程状态。默认回环监听和 host 白名单不能替代 token；仍不得暴露至外网。协议测试和非空合成 fixture 不等于真实 Word 驱动或产品验收。

## 真实 Word 验收矩阵

发布负责人须为每个宣称支持的平台分别复制下表：Windows 桌面 Word、macOS 桌面 Word、Word on the web。记录 OS、Word 版本/build、Office.js requirement set、浏览器/WebView、manifest 模式、部署 URL、构建指纹、模型/供应商、自动应用及跟踪设置。不支持的组合必须明确限制范围并经过 waiver，不可从另一平台推断通过。

所有用例使用脱敏可复现文档；至少包含英文、中文、中英混排、标题、列表、表格、图片、批注与已有修订。每行保存输入与预期、操作步骤、实际结果、输出 docx/截图、日志、执行人和时间。模型输出有随机性时记录模型版本及生成结果，不要求措辞完全相同，但范围、结构、授权、错误状态和保真约束必须可核验。

| ID | 场景与操作 | 必须观察的结果 | 初始状态 |
|---|---|---|---|
| W01 | 安装/侧载、打开与重开 taskpane，部署更新后重载 | HTTPS 可用、资源无缺失、指纹为本次构建、设置可恢复，无旧缓存误认 | not-run |
| W02 | 选区润色，中英混排、粗斜体/链接/列表 | 关闭自动应用时先有提案且文档不变；选择部分修改只影响所选范围，拒绝项未写；跟踪开启时可在 Word 检查修订 | not-run |
| W03 | 全文改写，长文、标题和多个 chunk，夹杂表格 | 分块完整、顺序正确、非目标内容与格式保留；跳过/不支持项明确可见，不把部分成功标成全成功 | not-run |
| W04 | 开启自动应用，多提案、重载设置、关闭后再提交 | 开关代表显式持续授权；回合结束后按序应用，不在生成途中写入；关闭后后续提案等待确认，无重复应用 | not-run |
| W05 | 提案后手动移动/修改目标，再定位和应用；双击及跨卡应用 | 正确定位或拒绝过期目标，绝不静默写错位置；互斥与重复应用保护有效 | not-run |
| W06 | 开/关跟踪模式，文本插删、格式调整并触发应用失败 | 结果与设置一致，原 Word 跟踪模式恢复；原生修订可接受/拒绝的范围如实记录 | not-run |
| W07 | 标题/字体/段落格式、插入标题、续写及复合任务 | 作用范围与顺序正确，不影响邻段或表格；多卡结果及失败边界明确 | not-run |
| W08 | 表格新建、单元格修改、行列结构/样式修改 | 实际维度、内容和格式正确；各平台跟踪差异与不支持项可见，无意外合并/删除 | not-run |
| W09 | SVG/独立图像供应商生成、插入、缩放、替换、alt/链接及图注 | 预览与实际图片一致、尺寸/定位正确；恶意 SVG/URL 不成为活动内容，图注编号/位置正确 | not-run |
| W10 | 冗余空段清理，文末和表格附近空段 | 仅删除可清理段，不破坏文档结构；提案与实际删除一致 | not-run |
| W11 | 批注/修订抽取、生成摘要新文档、Q&A | 摘要范围与来源正确，新文档可打开；Q&A 不改原文；HTML 清理有效且不被宣称能解决语义提示注入 | not-run |
| W12 | 取消、超时、断网、服务端错误、部分应用失败、重试 | 状态结束、错误可见、没有迟到的未授权写入；明确部分写入及恢复方式，重试不重复插入 | not-run |
| W13 | 配置本地/云端 chat 与独立 image 后端，检查请求和日志 | 只向配置的可信端点/代理上游发送所需内容；密钥不进入日志/截图，localStorage 明文风险已说明 | not-run |
| W14 | 附件、slash skills、自定义提示词与启用的 MCP 工具 | 使用正确上下文，持久化范围符合承诺，外部工具实际副作用与授权边界可追踪 | not-run |

## 发布状态与阻断规则

每项发布清单状态只能是 `passed`、`waived` 或 `not-run`，但须另存执行结果（包括失败及 blocker），不能用状态字段隐藏失败。

- `passed`：该项在声明的平台/设置和本次构建上确实执行，实际结果符合全部预期，有可追溯证据。命令退出 0 只能通过该命令负责的层级；skip、空用例、旧报告和 mock 不算 L4 通过。
- `waived`：尚未满足的项获明确风险接受，记录原因、影响范围、负责人/批准人、关联问题、替代证据和到期时间。它不是测试通过；代码作者/代理不得默默自我豁免。
- `not-run`：未执行、环境不可用、证据不完整或尚未通过。执行过但失败时在结果栏明确 `failed` 和失败证据，保持发布阻断，直到修复重验或获正式 waiver。

发布记录至少包含版本/提交、dirty 差异、构建与部署指纹、各层命令/证据链接、逐平台矩阵、执行结果、状态、阻断项和 waiver。必选项存在 `not-run`、未批准失败或过期 waiver 时，不得声称“产品验收通过”。L1-L3 全绿只能表述“自动化与构建门禁通过，真实 Word 验收未完成”。

本文件不附带本次发布批准；上表初始均为 `not-run`。真实 Word、真实模型、部署和容器验证必须由对应运行证据更新，禁止从文档存在、测试数量或历史成功推断通过。
